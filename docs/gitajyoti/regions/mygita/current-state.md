# MyGita current state

The current client supports fixture and API-backed implementations organized around Identity, Experience, and Journey. Route-level pages compose these features through public entry points, and asynchronous repositories isolate the UI from provider choice. Root-served source and built output both default to API and retain `?provider=fixture` as an explicit override.

Working capabilities include discovery, experience detail, batch choice, interest registration, password Account access, onboarding, journey display, activity completion, profile editing, and user-facing system states. The bearer session is stored in `sessionStorage`; learning content and artwork remain placeholders.

The client includes checked-JavaScript configuration, OpenAPI-generated runtime validators, normalized transport errors, timeouts and route cancellation, stale-navigation suppression, bearer-session handling, safe post-login destination restoration, accessible form pending/error states, reconnect retry, and automated repository-contract, fixture-integrity, transport, architecture-boundary, API-flow, rendered-browser, and production-build tests. Production output is minified and uses hashed JavaScript and CSS assets. The shared runtime contains no developer routes, reset controls, feature flags, or simulated OTP UI.

Identity, Experience, and Journey each have fixture and API providers implementing the same checked repository contract. API responses are runtime-validated against generated OpenAPI validators and normalized before they cross into the UI-facing domain model.

The browser fixture and mock-server seed data remain independently authored. They share four experience IDs and three batch IDs. The browser defines three concrete Gita Sāra activities and supplies generic placeholders for nine other IDs that have concrete mock-server records. The OpenAPI model, generated validators, adapter normalization, and compatibility tests now make this difference explicit. Automated server-backed flows verify both the complete OTP-based Gita Sāra journey and password Account creation, optional Profile skip, enrolment, sign-out, password login, and restored Journey state.

OpenAPI contract version 0.2 defines additive username/password Account creation and login operations. The client repository, fixture/API providers, primary registration/login pages, and server implement that boundary. The server-backed password lifecycle is covered by an automated API-provider flow. Profile setup is an optional post-registration step and remains accessible from the My profile menu. Existing OTP behavior remains available as a non-primary prototype option during this migration.

Data-use optimization Phases 1–4 are complete. OpenAPI 0.3 and Flask implement public catalogue and private MyGita manifests, card summaries, opaque equality-only versions, weak manifest ETags, strong summary/detail ETags, and conditional responses. Versioned memory/IndexedDB storage now drives Discover and Experience detail: cached summaries render before background revalidation, unchanged catalogues avoid summary downloads, and previously browsed unchanged details avoid another detail body.

Phase 5 is complete. OpenAPI 0.4 and Flask provide independently versioned Journey, interest, and activity-state reads. The client caches those projections and Profile separately per Account, composes them behind the stable Journey repository contract, renders saved state before scheduled revalidation, and downloads only a projection whose manifest version changed. Authentication and mutation responses prevent redundant reads, and route composition resolves Identity once for both page and shell.

The complete six-phase data-use optimization is verified. CI now includes deterministic cache and provider-parity tests, eight live Flask integration flows, and a real Chromium gate for IndexedDB, conditional request budgets, cached offline rendering, repeated detail reuse, accessible personalized greetings, and production-equivalent root serving. Request budgets are centralized, exact, and reported in [request-budget-verification.md](request-budget-verification.md); unexpected, missing, or duplicate calls fail the standard regression command. Sign-out, Account switching, and `401` session rejection retain durable data only inside isolated Account namespaces and prevent it from appearing in another authentication context.

The local Flask API has interchangeable JSON and SQLite persistence implementations. JSON remains the default; the opt-in SQLite store durably persists runtime Identity and Journey data. The shared 75-test server suite covers both stores. Tests and OpenAPI response verification use Flask's WSGI test client. Local development uses Flask's threaded development server, while `wsgi.py` provides the deployment-style application entry point.
